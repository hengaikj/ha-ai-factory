# HA AI Software Factory 需求基线

文档编号：REQ-HA-F00-001
状态：待 Review / Requirement Gate 未批准
项目：HA AI Software Factory

## 1. 项目背景

HA AI Software Factory 以 XZG AI Project Template 为基础，采用 XZG AI Software Engineering Skill v5.7 的阶段流程，面向 AI 原生软件项目的规范化交付。项目当前完成 Bootstrap，业务代码尚未开始。本基线用于明确本项目首个可交付版本要解决的问题、参与角色、主要流程和验收边界；它描述的是软件工厂本身，不代表工厂生成的某个具体业务系统。

目前的项目资料没有提供已批准的产品调研、用户访谈或目标组织规模。本文件中关于 MVP 能力的描述作为待评审需求基线，未决事项列于 Open Issues。

## 2. 项目目标

1. 为一个 AI 软件项目提供统一的阶段、任务、交付物和门禁管理方式。
2. 让项目参与者能够查看当前阶段、待完成工作、责任角色、门禁状态及相关证据。
3. 通过模板和明确的质量门禁，帮助团队按顺序完成 Requirement、Design、Contract、Development、Review、Integration 和 Release 等工作。
4. 支持 Orchestrator 协调 AI 工程角色与人工决策者，并在需求或契约存在歧义时显式记录待决事项。
5. 保留阶段决策、交付物版本和质量证据，便于复核项目是否满足进入下一阶段的条件。

## 3. 用户角色

| 角色 | 主要职责 |
| --- | --- |
| 项目负责人 / 需求提出者 | 创建或发起项目，说明目标与约束，确认需求和范围，处理需要人工决策的事项。 |
| Orchestrator | 维护项目阶段与任务状态，协调各工程角色，检查交付物是否齐备；不能替代独立 Review 或自行批准自己的评审。 |
| 工程 Agent | 按分配任务产出需求、产品、设计、契约、实现或集成相关交付物，并遵守项目规范。 |
| Reviewer / Gate 审核者 | 独立检查阶段交付物和证据，给出通过、退回或待澄清结论。 |
| 项目管理员 | 管理项目成员、角色和项目级配置（具体权限边界待确认）。 |

同一人员可兼任多个角色的规则、权限模型及是否支持外部协作者尚待确认。

## 4. 核心业务流程

1. **项目初始化**：负责人创建项目并登记名称、目标、技术约束和工程规范；系统或项目模板建立项目结构与初始状态。
2. **Discovery / Requirement**：负责人和 Orchestrator 收集背景与需求，形成需求基线；未澄清事项进入 Open Issues。需求经评审批准后才能进入后续阶段。
3. **产品与设计**：按顺序完成 Product、UX/UI、Design Handoff 所需的目标、用户流程和设计交付物，并按对应门禁评审。
4. **Contract**：定义并评审 API、数据、安全等接口契约。契约未批准前不得修改对应代码接口；歧义进入人工决策队列。
5. **Development**：在适用需求、设计和契约门禁获批后，按任务实现并记录构建、测试等证据。数据库表和字段须有中文 COMMENT，关键代码和函数须有中文业务注释。
6. **Review / Integration**：独立 Review 实现和质量证据；通过后执行集成并验证跨模块交付。未通过的工作退回处理并保留结论。
7. **Release**：满足发布门禁后形成发布交付物和记录。发布方式、环境及回滚要求待确认。

各阶段必须依序推进，不得以任务状态代替门禁批准。流程状态至少应能区分未开始、进行中、待评审、已通过、未通过和待人工决策；具体状态机待 Contract 阶段确认。

## 5. MVP 范围

本需求基线建议 MVP 聚焦单项目、可审计的工程流程管理：

- 建立项目并记录项目基本信息、技术栈、当前阶段和负责人。
- 展示固定工程生命周期及项目当前阶段、阶段门禁状态和未完成任务。
- 创建、分配、更新任务，关联任务说明、交付物和责任角色。
- 管理阶段交付物及其评审结论，支持通过、退回和待澄清结果。
- 记录 Gate 检查项、批准状态、评审人、时间和证据引用。
- 管理 Open Issues / HUMAN_DECISION_REQUIRED 项及其处理状态。
- 提供本项目采用的模板、规则和交付物索引，支持查看或下载文件。
- 保留关键状态变更记录，便于追踪阶段推进依据。
- 首版面向单一部署实例和有限项目成员使用；是否支持多项目和多租户由 Open Issues 决定。

上述项目管理功能属于需求建议，仍需 Requirement Review 批准后作为正式范围。

## 6. 非 MVP 范围

- 自动替代人工批准 Requirement、Design、Contract、Review 或 Release Gate。
- 自动生成并直接部署完整业务系统，或绕过契约批准修改接口。
- 通用代码托管、CI/CD、云资源编排和生产运维平台能力。
- 复杂组织层级、计费、租户隔离、项目市场或外部客户门户。
- 面向任意第三方模型的统一计费、训练、微调或模型托管平台。
- 自动判定法律、合规或安全风险并作最终批准。
- 未经评审确定的通知渠道、移动端、实时协作和高级报表功能。

## 7. 技术约束

- 后端：Java 17、Spring Boot 3、MyBatis-Plus、MySQL 8。
- 前端：Vue 3、TypeScript、Element Plus。
- Agent Runtime：Python、FastAPI。
- Java 包名：`com.hengaikj.ai.factory`。
- 数据库名称：`ha_ai_factory`。
- 所有数据库表和字段必须提供中文 `COMMENT`。
- 所有关键代码和函数必须提供中文业务注释。
- Git Commit 必须使用中文，格式为 `新增:`、`修改:`、`修复:` 或 `文档:` 加简短说明。
- 遵循 XZG AI Software Engineering Skill v5.7 生命周期：Discovery → Requirement → Product → UX/UI → Design Handoff → Contract → Development → Review → Integration → Release。
- Requirement、Design、Contract、Review 等适用门禁未通过，不得进入依赖该门禁的后续工作；契约未批准，不修改相应代码接口。
- 部署拓扑、身份认证、权限细节、模型供应商和具体非功能指标尚未确认。

## 8. 验收标准

本基线的 Requirement Gate 验收建议如下：

1. 本文档包含项目背景、目标、用户角色、核心业务流程、MVP 范围、非 MVP 范围、技术约束、验收标准和 Open Issues。
2. 用户角色和核心流程能够说明负责人、Orchestrator、工程 Agent 与 Reviewer 的职责及交接关系。
3. 生命周期顺序和门禁约束与 Skill v5.7、`docs/lifecycle.md` 及 `docs/quality-gate.md` 一致，不允许跳过阶段或由 Orchestrator 自行批准 Review。
4. MVP 与非 MVP 边界清晰；尚未批准或信息不足的范围被列为 Open Issues，而非表述为已确认事实。
5. 文档明确指出 Contract 未批准前不得修改接口，以及数据库中文 COMMENT、关键代码中文业务注释和中文 Git Commit 等项目约束。
6. 需求负责人和独立 Reviewer 完成评审，逐项记录结论；未解决的阻塞项保持未批准状态，不进入后续阶段。
